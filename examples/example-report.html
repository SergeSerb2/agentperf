Biggest wins: likely causes and fixes

1. Run agents in WSL2 with repos on the Linux filesystem likely

about +782 AgentMark
estimated, if the affected tests reached reference speed (gains overlap and do not add up)

This machine shows the slow native pattern: per-process and per-file costs are a large part of the limit. On the one PC where both sides were measured, WSL2 on the same hardware scored far above the native-Windows setup described in the evidence - the largest single change agentperf has measured, with those conditions attached. Agents start processes and touch small files all day; WSL2 does both at Linux cost. Keep repos on the Linux filesystem: under /mnt/c every file operation crosses to NTFS and small-file work gets slower than native Windows.

Evidence

  • Probe: this run is native Windows (os_family=windows), not WSL2.
  • Pattern: process starts and/or small files trail the WSL2 reference on this machine.
  • Measured on the bundled reference hardware (i7-12700K, October 2026): the native-Windows profile (third-party real-time antivirus and the Windows Search indexer active, shell commands through Git Bash) scored far below WSL2 on the same PC. That gap is everything that native setup added; it was not split into parts, and no run with scanning off exists. One PC, with those settings; your gap may be smaller.
  • Pattern: a shell start costs 50.6 ms here vs 3.7 ms on the WSL2 reference.

Fix

  • Install WSL2 (wsl --install) and run the agent inside it.
  • Clone repos inside the Linux filesystem (for example ~/code), never under /mnt/c.
  • Open them from Windows via \\wsl$ only for occasional file access.
  • If agents must stay native, use a Dev Drive and antivirus exclusions for code folders.

Affected tests: files.create, files.delete, files.edit, files.read, files.stat_walk, git.commit, git.diff, git.init_commit, git.log, git.status, git.status_dirty, git.worktree, process.exec, process.node, process.parallel, process.python, process.shell, search.grep, search.rg_files, search.rg_literal, search.rg_regex, transfer.copy, transfer.copy_tree, transfer.extract, transfer.read, transfer.write

2. Antivirus / endpoint security scanning likely

about +239 AgentMark
estimated, if the affected tests reached reference speed (gains overlap and do not add up)

Security scanning taxes every process start and small-file operation. On one measured PC (October 2026), native Windows with third-party real-time antivirus and the Windows Search indexer scored far below WSL2 on the same hardware (see the bundled profiles). Scanning is part of that gap. It was not measured on its own: that PC was never run with scanning off, and the native side also differed in shell (Git Bash) and Python version.

Evidence

  • Probe: real-time antivirus scanning is active.
  • Probe: endpoint security agent detected: endpoint security agent (name withheld).
  • Pattern: a shell start costs 50.6 ms here vs 3.7 ms on the reference. Raw compute is slow here too, so scanning is at most part of the gap; the CPU and its tools differ as well.

Fix

  • Exclude your code folders, package caches (npm, pip, cargo), and ~/.agentperf from real-time scanning.
  • On Windows, put code on a Dev Drive (ReFS) so Defender uses performance mode, or run agents in WSL2 with repos on the Linux filesystem.
  • On a managed machine, ask IT for a developer-folder exclusion instead of disabling protection.

Affected tests: files.create, files.delete, files.edit, files.read, files.stat_walk, process.exec, process.node, process.parallel, process.python, process.shell

3. Windows power plan possible

Gain not estimated.

The active plan is 'Balanced'. Balanced and saver plans can add latency to short bursts and I/O. This is a pattern, not a measurement: agentperf has not measured the gain from changing the plan, and the WSL2 reference ran on this same kind of plan on its host PC.

Evidence

  • Probe: powercfg reports 'Balanced'.
  • Note: the reference machine's host PC used a balanced plan too, so the plan alone cannot explain a gap to the reference.

Fix

  • If short bursts feel laggy, try High performance and rerun to measure the difference.

Affected tests: process.exec, process.node, process.parallel, process.python, process.shell

4. PowerShell start cost on Windows observed

Gain not estimated.

PowerShell starts in 634 ms vs 51 ms for Git Bash. Harnesses that run commands through PowerShell pay this per command.

Evidence

  • Measurement: diag.powershell 634 ms; process.shell 51 ms.

Fix

  • Prefer WSL2 or Git Bash execution for agents where the harness allows it.
  • Trim the PowerShell profile; the no-profile number is the floor.

Affected tests: not scored; paid per tool call that starts PowerShell
